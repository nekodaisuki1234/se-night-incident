# 初版設計 v0.1

## 確定事項と設計案の区別

確定事項は会話でユーザーが指定または了承した内容。以下のキャラ名・障害詳細・採点・画面配置は開発側の提案で、試作後に調整する。

### 確定事項

- 一般公開する、スマホ優先のゲーム。
- 主人公は金融系SESの中堅SE。夜間バッチが落ち、駆けつけ対応する。
- Linuxとジョブ管理、SQLを使って調査・復旧する。候補選択と手入力を併用する。
- 原因はランダム。ログ・状態・復旧方法を一貫したシナリオとして生成する。
- 間違ったジョブ停止などの誤操作で状況が悪化し、強く詰められる。
- リーダーへの確認が正解だが、無断操作も選べる。
- 社内はチャット、顧客はメールまたは電話。定型文と自由入力を併用する。
- 電話は着信音、通話風の文字表示、返答選択。実際の音声は不要。
- 夜間の本番障害らしい緊張感を重視する。
- 再実行、後続正常終了、処理件数確認、顧客報告まででクリア。
- チャット返信とコマンド操作の遅れにペナルティ。全体のリアルタイム性は重視しない。
- 初版はAIなし。後から接続できる拡張点を用意する。
- GitHubで管理する。リポジトリは非公開、ゲームの一般公開先は別途設定する。

### まだ確定していない細部

- プレイ時間は文脈から5〜10分を暫定目標とする。
- Linux＋JP1風ジョブ管理＋Oracle風SQLの架空環境を提案する。
- 初版の原因は以下の3種類を提案する。
- 他アプリへの移動中は猶予時間を止める案。一時停止の扱いも試作で調整する。
- 実装方式・公開先は未設定。GitHubへのコミットだけではゲームは公開されない。

## プレイの流れ

01:17、監視担当から「夜間売上集計が異常終了」の連絡。主人公が現地に到着したところから開始。

1. 社内の引き継ぎと顧客からの第一報を確認する。
2. ジョブ状態とログを見て、異常終了した処理を特定する。
3. SQL・ファイル・プロセスなどを調べ、根拠を集める。
4. 顧客に現状・確認済みの影響・次の対応を報告する。
5. 具体的な操作対象と根拠を添えてリーダーに確認する。または無断で実行する。
6. 原因を解消し、対象ジョブを適切な位置から再実行する。
7. 後続ジョブの正常終了と処理件数を確認する。
8. 顧客へ復旧報告して結果画面へ進む。

## スマホ画面案

- 上部：ゲーム内時刻、対象ジョブ、障害状態、未対応通知の件数。
- 下部タブ：調査・操作／社内／顧客。
- 調査・操作：ログ、ジョブ一覧、ターミナル履歴。候補ボタンを押すと入力欄に入り、編集してから実行できる。SQLも同様。
- 社内：リーダーと監視担当の会話。承認依頼・報告の定型文と自由入力欄。
- 顧客：メール一覧と返信。電話着信は画面に割り込む。
- タブを切り替えても入力中の文章・コマンドは保持する。
- 通知は短く、詳細は対象タブで読める。スマホキーボードで実行ボタンが隠れないようにする。
- 色は濃紺の業務画面を基本に、異常を赤、注意を琥珀、正常を緑で示す案。

## キャラクター案

### 社内リーダー：佐伯
正確な対象・根拠・操作内容を求める。確認には答えるが、対象のない「再実行していいですか？」には聞き返す。誤操作時は責任と収束方法を追及する。
例：「止める前にジョブ名を確認しましたか。いま止めたの、正常稼働中の別処理です。」

### 監視担当：森
初報とログの所在を提供する。対応が止まると催促する。運用手順内の操作を依頼できる。
例：「いまどこまで確認できていますか。顧客から再度問い合わせが来ています。」

### 顧客運用責任者：高橋
影響範囲、復旧見込み、報告時刻を求める。根拠のない断言と無報告に厳しい。
例：「原因調査中なのは分かりました。朝の業務への影響は確認できているんですか。」

技術判断と状況に応じて厳しくする。正しい報告・確認には情報や協力が返る。

## ランダム障害案

シナリオID単位で原因、観測できる情報、正しい復旧手順、影響、誤操作結果をセットで抽選する。リプレイ用にシードを保持する。原因を画面に直接表示しない。

### A：連携ファイル未着

- 初期状態：売上取込ジョブが入力ファイル不在で異常終了。集計は待機中。
- 根拠：ジョブログに INPUT FILE NOT FOUND。受信ディレクトリには前日分しかない。
- 調査：ジョブ状態、ログ末尾、受信ファイルの一覧と日時、処理履歴のSELECT。
- 対応：連携元への確認依頼。正しい対象・日付を添えるとファイル到着イベントが進む。
- 承認：到着した当日ファイル、未処理である根拠、再実行対象を添えて依頼する。
- 復旧：当日ファイルを確認し、取込から再実行、集計終了と件数を確認する。
- 誤操作：前日ファイルを当日分として使うと日付不整合。処理済み入力の強制再実行は重複処理につながる。

### B：ディスク容量不足

- 初期状態：中間ファイル作成ジョブが書込不可で異常終了。
- 根拠：ログに No space left on device。dfで対象領域の使用率が上限、duで古い作業ファイルが判明。
- 調査：ファイルの用途、日時、対象領域、ジョブの中断位置を確認する。
- 承認：削除するファイル範囲と、それが処理済み・保管済みである根拠を添えて依頼する。
- 復旧：許可された古い作業ファイルのみ整理し、空き容量確認、対象ジョブを再実行する。
- 誤操作：当日の入力や証跡を削除すると別障害・証跡喪失。ワイルドカード削除は危険。
- 仕様：模擬コマンドだけを処理し、ホストのファイル操作には渡さない。

### C：DBロック

- 初期状態：更新ジョブがロック待ちを経て異常終了。
- 根拠：ログにロックタイムアウト。模擬セッション一覧で待機元と保持元がつながる。
- 調査：SQL候補でロック・セッション・処理履歴を確認。別ジョブの業務目的も調べる。
- 承認：保持元セッションの所有者、対象業務、終了可否をリーダーに確認する。
- 復旧：関係者に解除を依頼するか、承認されたセッションを終了。ロック解消を確認して再実行する。
- 誤操作：別セッションや正常ジョブを停止すると、別系統の処理も異常終了する。
- 拡大障害：誤停止した系統の状態調査と再開を追加タスクにする。元障害だけ直してもクリアできない。

## 承認・操作

承認は操作対象・操作種類・適用範囲に結び付ける。「確認済み」のフラグ1つで全操作を許可しない。承認後に状態が変わった場合は再確認を求める。

操作は「リーダーへ確認」「無断で実行」のどちらも選べる。毎回の強制確認画面でテンポを損なわないよう、危険度に応じて表示する。

無断で成功：技術的には復旧するが手順評価が下がる。
無断で失敗：状態が悪化し、追及イベントが発生する。
承認どおりの操作でも対象を取り違えると誤操作になる。

## 遅延と緊張感

全体の常時カウントダウンより、未対応の返信・必要な操作に猶予を設ける。

- 返信遅延：催促→電話→リーダーへの苦情→信用低下。
- 操作停滞：進捗確認→強い追及→対応不能判定。
- 調査、根拠取得、承認依頼などの意味ある行動は進捗として扱う。
- 無意味な同一コマンド連打・同じ報告の再送では猶予を無限に延ばせない。
- 次回報告時刻の約束は対応する期限を変更するが、無期限の延長はできない。
- 長いログの閲覧・入力に必要な時間を見て猶予を調整する。
- 顧客対応中にも技術作業の催促はあり得るが、同時に解決不能な期限を課さない。
- ペナルティは段階的に表示し、初回の短い遅延だけで即終了しない。

## AIなしの会話と将来拡張

初版は定型文とルールベースの自由入力評価。自然言語の万能理解を装わない。

報告の評価項目：現状、確認済み影響、次の対応、次回報告、根拠との整合。
未確認の原因・復旧時刻を断言すると評価を下げる。不明と説明して調査方針を提示することは正当な対応。

定型文には意味を持つIDを与える。自由入力は日付・ジョブID・報告要素・肯定否定を確認し、曖昧な場合は聞き返す。単語が入っているだけで承認やクリアにしない。

会話処理をConversationProviderに分離し、初版はRuleBasedProvider、将来はサーバー経由のAIProviderに差し替える案。復旧状態、承認、勝敗はゲームエンジンが管理し、会話出力から直接状態を書き換えない。

## クリア・終了案

クリアには、原因解消、対象ジョブと後続の正常終了、必要件数の整合、拡大障害の解消、事実に合う顧客報告をすべて必要とする。

結果は技術対応、報告、手順遵守、追加障害で評価する。
- 模範復旧：確認・報告・検証を満たした。
- 復旧したが要反省：無断操作や報告遅延がある。
- 二次障害からの生還：誤操作後に両方の障害を収束した。
- 対応交代：信用・進捗の悪化で担当を外される。
- 業務開始に間に合わず：未解決のまま失敗。ゲーム内時刻は行動や遅延で進める。

結果画面で操作履歴と、どこで状況が変わったかを示す。実在顧客・実在の本番データは使わない。

## 制作順序と確認

1. 設計を保存：現在の段階。
2. 試作：スマホの3タブ、コマンド・SQL候補、社内チャット、メール、電話、1種類の障害。
3. ゲーム完成：3種類のランダム障害、承認対象、二次障害、遅延イベント、結果画面。
4. 検証：各原因の正常ルート、無断成功、別ジョブ誤停止、承認対象違い、未検証の虚偽報告、遅延、タブ切替・キーボード・着信表示。
5. 公開：公開先を設定してURLを確認。GitHubのコード公開範囲とゲームの公開範囲は別に管理する。

検証にはシナリオを指定できる開発用シードを使い、全原因が再現可能な状態で確認する。
